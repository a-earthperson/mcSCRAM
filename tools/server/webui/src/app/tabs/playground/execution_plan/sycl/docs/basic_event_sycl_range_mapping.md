# SYCL range mapping for the basic-event bitpack field

This note describes the `basic_event` kernel geometry for the `nus9601` example on the NVIDIA GeForce RTX 5060 Ti device reported as `sm_120`. The important correction to the generic SYCL description is that this is not an Intel Xe mapping: for this backend/device, the useful hardware analogy is:

- SYCL work-item -> CUDA thread / warp lane instance.
- SYCL sub-group of size 32 -> CUDA warp.
- SYCL work-group -> CUDA thread block / CTA.
- SYCL compute unit -> NVIDIA SM.

The data layer being visualized is a 2D grid of `bitpack_t` tiles. For `uint64`, each `bitpack_t` contains 64 Monte Carlo trial bits and is drawn as an `8 x 8` point tile. For the basic-event partition, the logical bitpack grid has:

- `M = num_events` rows.
- `N = bitpacks_per_batch` columns.
- One point inside a tile = one bit of one `uint64` bitpack.
- One tile = one `uint64` output produced by one `basic_event` work-item.

## Work-item

A work-item is one invocation of `basic_event::operator()`. In this kernel, one valid work-item is addressed by:

```text
global_id(0) = event_idx
global_id(1) = batch_idx
global_id(2) = bitpack_idx
```

and it writes exactly one `uint64` bitpack:

```text
sample_idx = batch_idx * bitpacks_per_batch + bitpack_idx
basic_events_block[event_idx].buffer[sample_idx] = bitpack_value
```

The `uint64` value is generated by Philox as 64 Bernoulli bits, so in the MathBox data layer this work-item owns one `8 x 8` bitpack tile.

## Sub-group

A sub-group is a contiguous set of work-items inside a work-group. On this device the only reported sub-group size is `32`, so a SYCL sub-group maps naturally to one CUDA warp. It is the main unit for lockstep SIMD/SIMT execution and memory coalescing.

## Work-group

A work-group is a 3D tile of work-items. On NVIDIA it maps to a CUDA thread block / CTA. Work-items in a work-group may use work-group barriers and local memory; work-items in different work-groups cannot synchronize inside a kernel.

## nd_range

An `nd_range<3>` is the pair:

```text
global_range = total launched 3D work-item lattice
local_range  = per-work-group 3D tile shape
```

For `basic_event`, the logical range is:

```text
[num_events, batch_size, bitpacks_per_batch]
```

The actual launched global range is rounded up in each dimension to a multiple of the chosen local range. Out-of-bounds work-items return without writing.

## Accessible overview

For the `nus9601` basic-event partition, the conceptual data layer is:

```text
num_events x bitpacks_per_batch
= 1567 x 184512 bitpack_t values
= 289,130,304 uint64 bitpacks
= 18,504,339,456 Monte Carlo bits
```

The MathBox model should therefore treat each row as one basic event and each column as one bitpack in that event's per-pass sample buffer. Each tile is an `8 x 8` visual grid because `bitpack_t = uint64` has 64 bits.

The kernel launch does not launch one work-item per bit. It launches one work-item per bitpack:

```text
one work-item -> one event_idx, one batch_idx, one bitpack_idx -> one uint64 output
```

For this example:

```text
logical_range = (1567, 1, 184512)
local_range   = (64,   1, 16)
global_range  = (1600, 1, 184512)
```

So one work-group covers a `64 x 16` tile of the bitpack data layer: 64 event rows and 16 bitpack columns. Since each bitpack tile has 64 visual points, one work-group corresponds to:

```text
64 events * 16 bitpacks/event = 1024 bitpack tiles
1024 bitpack tiles * 64 bits/tile = 65,536 visual points
```

The extra 33 rows in `global_range.x = 1600` are padding caused by rounding `1567` up to a multiple of `local_range.x = 64`. Those padded work-items fail the bounds check and do not write output.

## (0) SYCL geometry for `nus9601`

### Work-item

A valid basic-event work-item is identified by the 3D coordinate:

```text
(event_idx, batch_idx, bitpack_idx)
```

For the captured partition:

```text
event_idx   in [0, 1567)
batch_idx   in [0, 1)
bitpack_idx in [0, 184512)
```

The work-item computes one `uint64` bitpack:

```text
pdag_idx      = event_block[event_idx].index
sample_idx    = batch_idx * 184512 + bitpack_idx
iteration_idx = current outer sample-pass iteration
seed_base     = {pdag_idx + 1, event_idx + 1, sample_idx + 1, (iteration_idx + 1) << 6}
bitpack_value = philox_pack_64_bernoulli_bits(seed_base, probability_threshold)
```

`philox128.h` generates four Bernoulli bits per Philox generation because Philox 4x32 returns four 32-bit words. For `uint64`, the kernel performs 16 generations:

```text
64 bits / 4 bits per generation = 16 generations
```

Thus one work-item is computationally heavier than a single bit write: it performs the full counter setup, 16 Philox 4x32-10 evaluations, 64 threshold comparisons, bit packing, and one 64-bit global store.

### Work-group

The local range is:

```text
local_range = (64, 1, 16)
```

Therefore:

```text
work-items per work-group = 64 * 1 * 16 = 1024
```

This is the device-reported maximum work-group size. A work-group partitions the logical data layer as:

```text
64 event rows x 16 bitpack columns
```

The number of work-groups is:

```text
groups_x = 1600 / 64     = 25
groups_y = 1 / 1         = 1
groups_z = 184512 / 16   = 11532

total work-groups = 25 * 1 * 11532 = 288300
```

### Sub-group

The device reports:

```text
sub_group_sizes = [32]
max_num_sub_groups = 32
```

Since the work-group has 1024 work-items:

```text
1024 / 32 = 32 sub-groups per work-group
```

On NVIDIA this is exactly the CUDA warp view: each sub-group is one 32-lane warp. With a conventional row-major linearization of a 3D local id, dimension 2 (`z = bitpack_idx`) is the fastest-changing coordinate, so a warp in a `(64,1,16)` work-group naturally covers two event rows by sixteen adjacent bitpacks:

```text
warp/sub-group ~= 2 events x 16 bitpacks
```

That is a favorable memory shape: 16 adjacent `uint64` stores are 128 bytes, equal to the reported global cache-line size. A 32-lane warp therefore writes two 128-byte contiguous segments, one for each of two events, assuming the event buffers are aligned as intended.

## (1) Work-item shape and mapping to the bitpack data layer

The basic-event data layer is not a bit-level launch grid. It is a bitpack-level launch grid.

The native buffer layout is created by `create_basic_event_block`: all basic-event outputs are allocated as one contiguous device block of:

```text
num_events * num_bitpacks
```

where:

```text
num_bitpacks = sample_shape.num_bitpacks()
             = batch_size * bitpacks_per_batch
```

Each event's `buffer` pointer is offset by:

```text
event_idx * num_bitpacks
```

For `nus9601`:

```text
batch_size          = 1
bitpacks_per_batch  = 184512
num_bitpacks/event  = 184512
bytes/event         = 184512 * 8 = 1,476,096 bytes
bits/event          = 184512 * 64 = 11,808,768 bits
```

The basic-event partition has 1567 events, so resident memory for this partition is:

```text
1567 * 1,476,096 = 2,313,042,432 bytes
```

The mapping from kernel coordinates to the MathBox data layer is:

```text
MathBox tile row    = event_idx
MathBox tile column = bitpack_idx when batch_size = 1
MathBox tile point  = bit position in uint64, drawn as local 8x8
```

For a general `batch_size > 1`, the linear sample index is:

```text
sample_idx = batch_idx * bitpacks_per_batch + bitpack_idx
```

So the visual column can either remain a 2D `(batch_idx, bitpack_idx)` decomposition or be flattened as:

```text
visual_column = sample_idx
```

Your current MathBox type names already match the `batch_size = 1` `nus9601` case:

```text
bitpackRows    = num_events
bitpackColumns = bitpacks_per_batch
```

### `global_range` definition

`basic_event::get_range()` starts from the logical dimensions:

```text
global_size_x = num_events
global_size_y = sample_shape.batch_size
global_size_z = sample_shape.bitpacks_per_batch
```

Then it rounds each dimension up to a multiple of the corresponding local dimension:

```text
global_size_d = ceil(logical_size_d / local_size_d) * local_size_d
```

For `nus9601`:

```text
x: ceil(1567 / 64) * 64 = 25 * 64 = 1600
y: ceil(1 / 1) * 1 = 1
z: ceil(184512 / 16) * 16 = 184512
```

Hence:

```text
global_range = (1600, 1, 184512)
```

The kernel then checks:

```text
event_idx   >= event_block.count
batch_idx   >= sample_shape.batch_size
bitpack_idx >= sample_shape.bitpacks_per_batch
```

and returns early for padded coordinates. In this example only X has padding:

```text
padded event rows = 1600 - 1567 = 33
overprovisioned work-items = 33 * 1 * 184512 = 6,088,896
```

Those padded work-items correspond visually to rows beyond the real data layer; they should not be drawn as real bitpack data.

## (2) How `local_range` is chosen, and whether the assumptions hold

For a basic-event kernel, `kernel_builder.h` computes:

```text
local_range = working_set(queue, num_events_in_kernel, sample_shape)
  .compute_optimal_local_range_3d()
```

For GPU devices, `working_set::compute_optimal_local_range_3d_for_gpu()`:

1. Starts with the total work-group budget:

```text
max_work_group_size = 1024
log2(max_work_group_size) = 10
```

2. Allocates that power-of-two budget across X, then Y, then Z.

3. Caps each dimension by the device's reported 3D work-item limits:

```text
max_work_item_sizes_3d = (64, 1024, 1024)
```

For `nus9601`:

```text
target_x = num_events = 1567
hardware-capped x = 64
closest power of two = 64 = 2^6
remaining log2 budget = 10 - 6 = 4

target_y = batch_size = 1
local_y = 1 = 2^0
remaining log2 budget = 4

target_z = bitpacks_per_batch = 184512
hardware-capped z = 1024
closest power of two = 1024 = 2^10
remaining budget only allows 2^4
local_z = 16
```

So:

```text
local_range = (64, 1, 16)
```

### Assumptions baked into this choice

The heuristic assumes:

- A full 1024-work-item work-group is desirable on GPU.
- X should get priority until it reaches either the number of events or the device's 3D X limit.
- Y should represent batch count, but the sample shaper often flattens all sample work into Z, making Y equal to 1.
- Z should receive remaining work-group budget and should ideally align with memory/cache behavior over contiguous bitpack stores.
- Power-of-two local dimensions are preferable.
- The backend maps sub-groups to 32-lane warps, so multiples of 32 work-items per group avoid partial sub-groups.

For this `nus9601` / RTX 5060 Ti example, these assumptions mostly hold:

- `batch_size = 1`, so `local_y = 1` is exactly right.
- `bitpacks_per_batch = 184512` is large and divisible by `16`, so `local_z = 16` creates no Z padding.
- `local_z = 16` matches the reported 128-byte cache line for `uint64`: `16 * 8 bytes = 128 bytes`.
- `local_range.product = 1024`, which gives 32 full sub-groups/warps per work-group.
- The launch has 288,300 work-groups, so there is far more block-level parallelism than the 36-SM device needs for saturation.
- X padding is modest relative to the whole launch: `6,088,896 / 295,219,200 ~= 2.06%`.

The main caveats:

- A 1024-thread block is maximum-sized. It gives exactly 32 warps per block, but it may reduce block residency per SM depending on register allocation and shared/local memory usage. The kernel does not appear to use significant local memory, but Philox is arithmetic/register-heavy, so register pressure is the likely occupancy limiter.
- The current `std::clamp(target, target, max_limit)` idiom in `working_set.h` is conceptually intended to cap by hardware limits, and it produces the captured result here under common implementations. Formally, `std::clamp` requires `lo <= hi`, so `target > max_limit` is not a clean expression of that intent. The observed plan should be read as "cap target by the hardware dimension limit."
- The heuristic does not explicitly query measured occupancy, register count, or backend block scheduling behavior. It is a shape heuristic, not a full CUDA occupancy model.

## (3) SYCL work geometry mapped to `sm_120` hardware

The captured device information says:

```text
device name         = NVIDIA GeForce RTX 5060 Ti
version             = sm_120
max_compute_units   = 36
CUDA cores          = 4608
CUDA cores per SM   = 4608 / 36 = 128
sub_group_sizes     = [32]
max_work_group_size = 1024
local_mem_size      = 49152 bytes
global cache line   = 128 bytes
```

For this backend, the practical mapping is:

| SYCL concept | NVIDIA/CUDA concept | In this example |
|---|---:|---:|
| work-item | CUDA thread / lane instance | one `(event,batch,bitpack)` producer |
| sub-group | warp | 32 work-items |
| work-group | CTA / thread block | 1024 work-items |
| compute unit | SM | 36 SMs |
| local memory | shared memory | 49,152 bytes reported |
| global memory | device DRAM through cache hierarchy | 128-byte line reported |

The important conceptual point is that a CUDA core is not a permanent home for one SYCL work-item. A work-item is a logical thread. Work-items are grouped into warps. Warps from resident CTAs are scheduled on an SM. The SM issues warp instructions; active lanes execute the instruction over the SM's execution resources. The device has 128 FP32 CUDA cores per SM, but a warp is still 32 lanes, and latency hiding comes from having many resident/schedulable warps, not from statically assigning one work-item to one CUDA core.

For the `basic_event` launch:

```text
work-groups total = 288300
SMs               = 36
average CTAs/SM over the whole launch stream = 288300 / 36 ~= 8008
```

That does not mean 8008 CTAs are resident at once. It means the launch has enough CTAs that the scheduler can keep all SMs busy for a long time. At any instant, each SM holds some number of resident CTAs limited by:

- max resident threads/warps/blocks for the architecture,
- registers per thread,
- shared/local memory per block,
- compiler/backend resource allocation,
- block size, here 1024 threads.

Because each work-group already contains 32 warps, a single resident block supplies substantial warp-level parallelism. Additional resident blocks improve latency hiding only if resources allow them.

## (4) Visualization implications for MathBox

The useful visual hierarchy is:

```text
bit -> point inside 8x8 tile
bitpack_t -> 8x8 tile
work-item -> one bitpack tile
sub-group / warp -> 32 work-item tiles
work-group / CTA -> 64 x 16 bitpack-tile rectangle
global_range -> many work-group rectangles over the full data layer, with padded rows at the end
SM -> runtime hardware executor that receives CTAs; not a static region of the data layer
```

For an interactive MathBox view, the best first focus is one work-group-sized window:

```text
64 event rows x 16 bitpack columns
```

Within that window:

- Draw the existing `8 x 8` bitpack tiles as the base data layer.
- Overlay one work-item boundary per bitpack tile.
- Overlay sub-group/warp regions as groups of 32 adjacent work-items. Under conventional 3D row-major linearization with Z fastest, this is visually `2 x 16` bitpack tiles.
- Overlay the full work-group as a `64 x 16` rectangle.
- Optionally show the X padding region separately for the final work-group strip: real rows `0..1566`, padded rows `1567..1599`.

Do not draw SMs as fixed partitions of the global data layer. CTAs are dynamically scheduled onto SMs. A truthful hardware overlay should instead show an animation or annotation such as:

```text
36 SMs consume a queue of 288300 work-groups.
Each work-group contains 32 warps.
Each warp contains 32 work-items.
Each work-item writes one uint64 bitpack tile.
```

For a static diagram, a reasonable assumption-based hardware view is:

```text
At time slice t:
  each active SM owns one or more resident work-groups;
  each resident work-group contributes 32 warps;
  warp schedulers issue ready warps;
  each warp processes 32 bitpack-producing work-items.
```

That makes the implicit execution piece visible without falsely implying that a particular event row or bitpack column permanently belongs to a particular CUDA core.
